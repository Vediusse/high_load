# Lab4: четыре сценария Postman

## Импорт

Импортировать **два файла** через Import:

1. `lab4.postman_collection.json` — коллекция **Lab4 — 4 повторяемых сценария**.
2. `lab4.local.postman_environment.json` — готовые локальные доступы.

Выбрать справа сверху environment **Lab4 — local (private)**. Локальный файл уже
создан для текущего стенда. При необходимости сформировать его заново из `.env`:

```bash
python3 scripts/setup-postman.py
```

Если старая плоская коллекция уже импортирована, переимпортировать обновлённый
`lab4.postman_collection.json` с заменой прежней. Environment можно оставить тот же.

Публичный `lab4.postman_environment.json` — шаблон с пустыми паролями для другого
компьютера. Локальный environment содержит секреты, имеет права `600` и исключён
из Git и контекста Docker. GitHub-токен в Postman не требуется.

Использовать Postman Desktop либо Desktop Agent: Cloud Agent не обращается к
`localhost` вашего компьютера. Gateway: `http://localhost:18084`.

## Повторный запуск

Для всей коллекции: **Run collection**, 1 или несколько iterations. Для отдельного
сценария: меню нужной папки → **Run folder**, все запросы папки, начиная с первого.
Рекомендуемый Delay — **100 ms**. ID, версии, будущая дата, логины, пароли тестовых
ролей и JWT подставляются автоматически. Ничего копировать между запросами не надо.

Каждая папка создаёт собственных пользователей, организацию и заказ. Имена имеют
новый случайный суффикс на каждой итерации, а переменные разделены префиксами
`biz_`, `files_`, `notify_`, `runtime_`. Папки независимы; их можно запускать в любом
порядке, сколько угодно раз. Созданные данные сохраняются для просмотра. Проверки
удаляют только специально созданные этим прогоном экземпляры.

Все HTTP-запросы видны в списке. Ожидание событий Kafka повторяет только GET,
с ограничением `pollTimeoutMs=60000`; скрытых `pm.sendRequest` нет. При ручном Send
выполнять шаги сверху вниз; запрос «дождаться» при необходимости отправить повторно.

| Папка | Что демонстрирует |
| --- | --- |
| 01 — Бизнес, 40 запросов | Supervisor создаёт менеджера клиентов, менеджера кухни и представителя. Организация → точка выдачи → категория/блюдо → DRAFT → позиции → SUBMITTED → CONFIRMED → IN_COOKING → READY → COMPLETED. Цена в заказе остаётся прежней после изменения каталога. История/changedBy, отклонение, отмена, изменение/удаление черновика, ошибки 409/403. |
| 02 — Файлы, 41 запрос | Свои роли/заказ → PDF в локальный S3 → скачивание и SHA-256 → метаданные/ссылка Order → чтение коллегой и запреты чужой организации → MIME/сигнатура/ранний акт → логическое удаление временного файла → READY → акт и скачивание. |
| 03 — Уведомления, 32 запроса | Submit уведомляет кухню; confirm/cooking/ready/completed уведомляют представителя. Лента, отметка прочтения, повтор без изменения readAt, запрет чужого notificationId. |
| 04 — Runtime, 26 запросов | Политика до refresh → существующий PDF → сигнал Kafka → ожидание новой политики → большой PDF 201/413 в зависимости от лимита → маленький 201 → прежний файл скачивается. |

## Подпапки: основной путь и отдельные проверки

Родительские папки теперь содержат подразделы. Для автоматического полного
прогона выбрать родительскую папку; Runner проходит её дерево сверху вниз.
Для ручного показа сначала выполнить «00 — Подготовка», затем нужные части.
Подпапка — этап сценария с уже созданными данными, а не новая независимая итерация.

```text
01 — Бизнес
  00 — Подготовка: роли, организация, меню
  01 — Основной путь: заказ → кухня → выдача → итоговый GET
  02 — Отдельный случай: отклонение
  03 — Отдельный случай: отмена
  04 — Черновик: изменить, конфликт версии, удалить
  05 — Проверка ролевого запрета
02 — Файлы
  00 — Подготовка и подтверждённый заказ
  01 — Спецификация: загрузка → одно скачивание → метаданные/связь
  02 — Отдельно: права коллеги и чужой организации
  03 — Отдельно: MIME, сигнатура, ранний акт
  04 — Отдельно: удаление временного файла
  05 — Акт: READY → загрузка → скачивание акта
03 — Уведомления
  00 — Подготовка
  01 — Заказ отправлен: уведомление кухни
  02 — Подтверждение: лента и прочтение
  03 — Отдельно: чужие уведомления
  04 — Приготовление и выдача
  05 — Итоговая лента / Visualize
04 — Runtime
  00 — Подготовка
  01 — Действующая политика и файл до изменения
  02 — Применить Git commit через Kafka
  03 — Проверить реальное поведение
  04 — Отдельно: запрет для представителя
  05 — Итоговая политика
```

У спецификации один запрос скачивания в основном пути. GET коллеги/чужой
организации вынесены в проверку прав и подписаны «Проверка доступа». Скачивание
акта находится в его отдельной подпапке. Повторный финальный GET спецификации убран.

## Файлы: скачать и показать S3

PDF уже встроены в коллекцию: настраивать Working directory и выбирать путь
к файлу не нужно. Это настоящие открываемые одностраничные PDF, а не строка
с сигнатурой. Копии находятся в `fixtures/`.

После запуска папки **02**:

1. Открыть подпапку **01 — Спецификация** и запрос **OWNER — скачать file / Send and Download**.
2. Нажать **Send and Download** или **Save response → Save to a file**, сохранить
   с расширением `.pdf` и открыть. Спецификация и акт остаются `ACTIVE`.
3. Список файлов заказа и ответ загрузки показывают ID, MIME, размер и SHA-256.
4. Открыть [S3 Console](http://localhost:19001), войти по `ADMIN-ACCESS.local.md`:
   `order-files → documents`. Объект имеет UUID-ключ, исходное имя хранится в PG.

`files_fileId` и `files_actId` — последние активные файлы; `files_orderId` — заказ.
Если JWT спустя 15 минут истёк, повторить только запрос **OWNER — вход** из этой
папки, затем скачивание. Первый запрос папки создаст уже новый прогон.

## Уведомления: как показать преподавателю

Запустить папку **03**, открыть последний запрос **Итоговая лента** и вкладку
**Visualize** в ответе. Таблица показывает тип, текст, заказ, дату создания и дату
прочтения. В обычном JSON видны те же данные.

В запросах «дождаться ORDER_SUBMITTED» и «дождаться ORDER_CONFIRMED» используются
разные JWT: кухни и представителя. В конце видно четыре уведомления представителя,
одно прочитанное; попытка чужого пользователя отметить наш ID возвращает `404`.

## Runtime: почему localhost:18889 показывает Not Found

`http://localhost:18889/` — корень служебного REST-порта **без главной страницы**.
`404` здесь ожидаем. Точные адреса:

| Адрес | Назначение |
| --- | --- |
| `GET http://localhost:18889/actuator/health` | Проверка Config Server, `200 UP`. |
| `POST http://localhost:18889/actuator/busrefresh/file-service:**` | Сигнал обновления через Kafka; отдельный Config operator, JSON Content-Type, ответ `204`. Папка 04 отправляет всё сама. |
| `GET http://localhost:18084/api/v1/files/settings` | Реально применённая политика; JWT **SUPERVISOR**. Без токена `401`. |
| [Swagger](http://localhost:18084/swagger-ui/index.html) | Выбрать File Service → Runtime-config → settings. Сначала войти как SUPERVISOR и Authorize. |

В Swagger читается действующая политика. Значения редактируются в **Git**, потому
что это источник конфигурации. Endpoint для произвольной записи `busenv` закрыт.
Kafka передаёт сигнал refresh, после которого клиент перечитывает Git.
Обновление политики File не пересоздаёт Eureka-клиент; его соединение сохраняется.
Новые подписчики Bus начинают с актуальных сигналов, а бизнес-consumers сохраняют
прежнюю обработку событий с начала/сохранённых offsets.

### Демонстрация лимита 10 MiB → 2 KiB → 10 MiB

Всё редактирование можно выполнить в [готовом веб-редакторе GitHub](https://github.com/Vediusse/high_load_configs/edit/lab4/file-service/application.yml):
изменить `files.max-bytes`, нажать Commit changes в ветку `lab4`, выставить
`expectedFileMaxBytes` в Postman и выполнить runtime-подпапки 02 → 03 → 05.
До этого один раз нужны 00 → 01, либо можно каждый раз запускать всю папку 04.
Это сохраняет config-repo источником значений. После веб-правок перед CLI-helper
обновить локальный `high_load_configs_lab4` командой `git pull --ff-only`.

Схемы и объяснение сборки/старта/runtime: [карта проекта](../docs/PROJECT-MAP.md).

Начальное состояние: в выбранном environment `expectedFileMaxBytes=10485760`.
Папка **04** проходит и без изменения Git — повторный refresh допустим.

1. Из корня `/Users/rublev/DEV/high_load_lab4` изменить **только Git**:

   ```bash
   python3 scripts/demo-runtime-config.py --max-bytes 2048
   ```

   Команда меняет `file-service/application.yml` в соседнем `high_load_configs_lab4`,
   делает commit/push в `lab4`. Живой сервис она **не обновляет**.
   При повторе того же значения лишний commit не создаётся.

2. В environment Postman поставить **`expectedFileMaxBytes=2048`** и сохранить.
   Запустить папку **04 с первого запроса**. Показать:

   - «политика ДО refresh»: старый лимит и `generation`;
   - «отправить refresh»: `204`, сообщение идёт через Kafka;
   - «дождаться политики»: `limits.maxBytes=2048`, новое `generation/appliedAt`;
   - загрузка большого PDF: `413`, маленького: `201`;
   - PDF, сохранённый до refresh, продолжает скачиваться.

3. Вернуть исходную настройку в Git:

   ```bash
   python3 scripts/demo-runtime-config.py --restore
   ```

4. Поставить **`expectedFileMaxBytes=10485760`**, снова Run папки **04**.
   Лимит вернётся к 10 MiB; большой PDF теперь получает `201`.

Повтор того же сценария с тем же лимитом тоже проходит; `generation` может остаться
прежней, если значения уже применены. Не нужно искусственно менять generation.
Если ожидаемый лимит не закоммичен/не запушен, GET закончит ожидание с понятной
ошибкой, вместо успешного отчёта с неприменёнными настройками.

Подтвердить, что процесс File Service не перезапускался, — выполнить до и после:

```bash
docker inspect high-load-lab4-file-service-1 --format '{{.State.StartedAt}}'
docker compose exec kafka-1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --describe --topic runtime-config-events
```

Должно совпасть `StartedAt`; топик имеет 3 partitions, RF3, minISR2. Дополнительные
схемы и SQL сопоставления метаданных/объектов — в `docs/lab4-s3-runtime.md`.

## Запуск без интерфейса

```bash
npx --yes newman@6.2.3 run postman/lab4.postman_collection.json \
  -e postman/lab4.local.postman_environment.json \
  --iteration-count 2 --delay-request 100 --bail
```

Генератор коллекции: `python3 scripts/build-postman.py`. Старый файл
`business-scenarios.postman_collection.json` сохранён для предыдущих лабораторных;
для этой защиты импортировать **lab4.postman_collection.json**.
