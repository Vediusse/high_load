Корпоративное питание — фактическая архитектура лабораторной 4

Сохранён бизнес принятой lab3: собственная кухня, постоянное меню, организации,
точки выдачи, ручное решение по целому заказу. Только Order меняет статус заказа.
Нет оплаты, склада ингредиентов, курьеров, внешних email/SMS/push или ML.

Владельцы данных
Catalog: категории/блюда/цены, PostgreSQL и R2DBC.
Order: организации/точки/заказы/строки/снимки/история/квитанции команд/ссылки на файлы,
PostgreSQL и JPA. Kitchen: рабочая проекция и production outbox, отдельная PG/JPA.
Identity: пользователи/роли/BCrypt/текущая организация и версии токенов, PG/JPA.
Notification: уведомления и inbox, отдельная PG/JDBC.
File: метаданные и outbox в PG/JDBC, бинарные данные в локальном S3 Silo.
Silo хранит объекты в отдельном s3-data Docker volume, доступ через AWS SDK S3Client.
Gateway, Config, Discovery — инфраструктурные приложения; common — библиотека.

Синхронный граф
Клиент -> Gateway -> Catalog / Order / Kitchen / Identity / Notification / File.
Gateway -> Identity: проверка текущего пользователя и обмен внешнего JWT на RS256
внутренний proof одного допуска. Остальные сервисы проверяют proof локально.
Kitchen -> Order -> Catalog: идемпотентная команда, цены и снимки.
Identity -> Order: активная организация при назначении представителя.
File -> Order: текущие права на заказ и его статус через минимальный внутренний API.
Пользовательский JWT передаётся явно и никогда не хранится для асинхронной работы.

Событийный граф
Order -> outbox -> order-events: submitted/confirmed/rejected/cancelled/completed.
Kitchen -> local projection + outbox -> production-events: cooking-started/ready.
File -> metadata + outbox -> file-events: uploaded/deleted.
Notification читает все три топика, Kitchen — подтверждение/отмену,
Order — file-events для fileId/type references. Notification получает активные
scoped user IDs из защищённого внутреннего Identity API с отдельным env credential.

Три KRaft broker/controller, IDs 1/2/3, отдельные persistent volumes. Основные топики
и DLT: 3 partition, RF3, min ISR2. Key=orderId. Envelope version1 с UUID eventId,
eventType, aggregateId, occurredAt и минимальным payload. FileVersion защищает
ссылки от позднего upload после delete. Между топиками общего порядка нет.

Атомарность
Состояние + история + outbox — одна локальная TX. Relay ставит sent_at после ack;
неотправленные строки сохраняются, retries/network waits/batches ограничены.
Старейшее неотправленное событие агрегата предшествует следующим.
Consumer effect + processed_event — одна TX, offset после неё. Повторы подавляются
DB uniqueness. Poison после bounded retries -> DLT; ошибка DLT не теряет original.
Kitchen использует прежние command IDs и receipt; повтор не меняет исходный аудит
Order. Production event не приписывает действие повторному вызывающему пользователю.

Слои
В каждом из шести бизнес-сервисов domain не импортирует Spring/JPA/R2DBC/Kafka/FS.
Application зависит от domain и портов. REST/Kafka — inbound; Feign/PG/storage —
outbound; configuration задаёт wiring и TX. ArchUnit проверяет направление.
JPA persistence metadata вынесена в META-INF/*-domain.hbm.xml. Catalog сохраняет
реактивные R2DBC-транзакции; JPA/JDBC/Feign/files вынесены с event loop на bounded
BlockingRequests. Бизнес-сервисы не зависят от JAR друг друга.

Файлы
Уникальный storage UUID, условный S3 PutObject, проверка MIME/signature/size и SHA256.
Order хранит fileId/type/version/deleted, File владеет метаданными и содержимым.
Download: текущий доступ к заказу + checksum. Delete: владелец + текущий доступ;
логическое удаление, bytes retained. Metadata/outbox rollback очищает доказанный
новый orphan; неизвестный результат commit не удаляет возможно действующий binary.
Спецификация — confirmed/in-cooking/ready/completed; акт — ready/completed.

Конфигурация и вход
Config Server читает отдельный Git repo high_load_configs, ветка lab4. Shared
application.yml плюс <service>/application.yml; секреты приходят только из env.
Gateway — вход бизнес-API. S3 API/Console и Config management опубликованы только
на localhost для оператора. Внутренние бизнес-пути не маршрутизируются
наружу. Swagger открыт, бизнес API защищён ролями, пользователем и организацией.
Точные операции, env, команды и ограничения: README.md и docs/lab4-run.md.

Runtime: Config Server публикует Spring Cloud Bus refresh в runtime-config-events
(3 partitions/RF3/minISR2). Все девять приложений слушают шину; получатель перечитывает
Git. FilePolicy атомарно применяет проверенные max-bytes/allowed-mime-types;
невалидный набор сохраняет последнюю рабочую политику. S3 endpoint/ключи/bucket и
жёсткий предел 10 MiB задаются при старте. Значения/секреты через Kafka не передаются.
POST busrefresh требует отдельного CONFIG_ADMIN; busenv запрещён. GET files/settings
показывает только действующую политику и generation супервизору через Gateway.
Подробности и демонстрация: docs/lab4-s3-runtime.md.
Kafka Binder шины явно использует ByteArraySerializer/Deserializer; бизнес-каналы
сохраняют StringSerializer/Deserializer. Подтверждения Bus не наследуют настройки
сериализации outbox.


Проверка архитектуры и читаемости 2026-11-18

Clean Architecture определяется зависимостями, а не количеством каталогов.
Domain содержит инварианты CorporateOrder/Dish/Organization, policy файлов и
модели событий. Application координирует сценарии и вызывает свои порты.
HTTP/JWT/multipart и Kafka listener находятся в adapters/in. Spring Data,
JDBC, Feign, подпись JWT и S3 — adapters/out. Configuration собирает
реализации и границы транзакций. Подпись токенов Identity доступна REST через
InternalTokens; прямой импорт реализации REST-адаптером удалён.

ArchUnit проверяет все шесть бизнес-сервисов: domain не зависит от framework,
ORM, JSON, application, adapters и файлового API; application не зависит от
Spring, ORM, JDBC, Kafka/Feign, JSON/Swagger и внешних adapters; inbound не импортирует outbound.
В Catalog application используются Mono/Flux для принятого реактивного стека;
Jakarta constraints на application input DTO описывают ограничения входа.
Это практическое разделение слоёв; полная независимость application от любых
библиотек не заявляется. Gateway, Config, Discovery являются техническими
сервисами, поэтому фиктивные domain/use-case пакеты в них не добавляются.

Составные входы оформлены как application DTO/commands/query: CreateOrderRequest,
UploadFileCommand, OrderSearch. Простые id/version параметры сами по себе не
нарушают разделение. HttpRequest, Jwt, FilePart не проходят в application.
SQL/HQL остаётся в persistence adapters. Простые выборки кухни заменены derived
query methods, создание категории — R2dbcEntityTemplate. Оставшиеся запросы
нужны для составных фильтров, cursor pagination, связей и атомарного upsert.
SQL для outbox/inbox и защиты порядка не заменяется неатомарным read-then-write.

Пустые старые каталоги удалены; единый формат поддерживают Spotless и .editorconfig.
Простые assignment-only конструкторы заменены @RequiredArgsConstructor; обычные
аксессоры используют @Getter. Конструкторы с проверками и инициализацией,
а также методы, защищающие инварианты/коллекции, остаются явными.

Готовность к production

Это проверенный учебный стенд. Лабораторная не включает TLS/ACL Kafka,
централизованный secret manager, off-host backup/restore, дежурство и нагрузочные
SLO. Три combined KRaft broker/controller и один локальный S3-узел достаточны для
проверки задания, но не являются планом эксплуатации кластера в production.
Репликация не заменяет резервное копирование; DLT требует операционного разбора.

https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
