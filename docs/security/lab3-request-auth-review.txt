Проверка схемы «одна проверка актуальности на внешний запрос»
Дата: 2026-10-09. Архитектурный разбор по запросу пользователя.
Статус: историческое обоснование; пользователь принял решение о реализации.
Актуальная редакция — lab3-contract.txt и lab3-request-auth.txt.

1. Вывод

Формальные требования, перечисленные пользователем, не запрещают проверку
актуальности пользователя один раз на входящий запрос и последующую локальную
проверку подписанного внутреннего JWT. Механизм подходит синхронным цепочкам
Gateway -> Kitchen -> Order и Gateway -> Order -> Catalog, если отзыв доступа
действует на новые внешние запросы, а уже допущенная цепочка может завершиться.

Рекомендуется для этой цели, но не объявляется универсально лучшим или уже
доказанно быстрым. Сокращение обращений к Identity доказуемо по схеме, выигрыш
по latency/throughput требует нагрузочного сравнения. Identity остаётся
обязательной зависимостью допуска новых запросов; появляется стоимость выпуска
внутреннего JWT и управления ключами. Без требования свежей проверки на входе
локальная проверка обычного короткоживущего access JWT была бы проще.

Проверка JWT и ролевой/объектной авторизации остаётся на КАЖДОМ сервисном входе.
Один раз выполняется только чтение актуальности пользователя в Identity DB.
Это одна логическая проверка состояния, не обещание ровно одного SQL-запроса.

2. Трассировка семи требований пользователя

- Добавить авторизацию: закрытые маршруты и deny-by-default сохраняются.
- Spring Security + JWT в Authorization: внешний и внутренний запросы используют
  Authorization: Bearer; внутренний токен проверяется Resource Server/Nimbus.
- Ролевая модель: четыре прежние роли, проверка в сервисе владельца операции.
- Логика текущего пользователя: проверенные sub/roles/organizationId определяют
  область данных и автора; роль не отменяет фильтр организации и бизнес-инварианты.
- Не отдавать пароль: UserResponse/CurrentUserResponse, JWT и логи не содержат
  password/passwordHash. Входной login/create DTO принимает пароль, иначе вход
  и создание по паролю невозможны. Формулировка про «запрос» не означает запрет
  передачи пароля серверу во входном DTO; это согласуется с артефактами проекта.
- Хэширование: BCrypt/PasswordEncoder сохраняются, схема не затрагивает хранение.
- Создание только supervisor: проверка SUPERVISOR в Identity сохраняется;
  прохождение Gateway или наличие внутреннего JWT сами по себе права не дают.

3. Найденные расхождения с текущими решениями проекта

А. docs/security/lab3-contract.txt, разделы 4-5: каждый вход в сервис вызывает
   validate без кэша; следующий вход после блокировки обязан отказать.
   Новый вариант меняет границу отзыва на новый внешний запрос. Уже выданное
   внутреннее подтверждение действует до exp с учётом явно выбранного допуска.
   Это различие нужно отразить в контракте и проверках AUTH-04/AUTH-05/AUDIT-01.

Б. Раздел 4: HS256 с общим секретом, RS256 запрещён текущим allowlist.
   Общий HMAC-секрет не обеспечивает единственного издателя: каждый проверяющий
   способен подписывать. Рекомендуется отдельный внутренний RS256-профиль:
   закрытый ключ только у Identity, открытый ключ у проверяющих сервисов.
   Существующий внешний HS256 можно сохранить и оставить его секрет в Identity.
   Это изменение проектного решения, не новая платформа и не нарушение JWT-ТЗ.
   Нужно уточнить фразу о подписывающем секрете в references/design.md, правила
   алгоритмов, env/Compose и тесты; нельзя просто расширить один общий allowlist.

В. Раздел 5 и permissions: исходный пользовательский JWT сейчас запланирован
   на всех Feign-вызовах. Целевой бизнес-контур должен принимать только внутренний
   профиль; прямой внешний JWT не должен обходить допуск Gateway/Identity.

Г. Прежний validate возвращает 204, а не подписанное подтверждение. Нужен
   отдельный внутренний обмен или явное изменение контракта, с проверкой
   вызывающего Gateway и запретом переобмена внутреннего JWT для продления TTL.
   Закрытый URL/Compose-сеть сами по себе не доказывают личность Gateway.
   В старом контракте нет отдельного технического credential: это тоже нужно
   согласованно пересмотреть, не вводя новую пользовательскую роль.

Д. В Артефакты/05 написано, что подтверждение и приготовление требуют разных
   ролей, но первичная матрица в Артефакты/06 задаёт KITCHEN_MANAGER для обоих.
   Это ранее разрешённое противоречие: сохраняется матрица и четыре роли,
   дополнительная роль ради примера из задания не создаётся.

Ни одно из этих расхождений не является запретом механизма в присланном ТЗ.
Но нельзя объявлять переход выполненным, сохранив старые проверки и документацию.

4. Рекомендуемая граница доверия

Gateway принимает внешний Bearer для каждого нового защищённого бизнес-запроса
и один раз обращается к Identity. Identity проверяет подпись/claims и актуальные
ACTIVE/version/roles/organizationId, затем выпускает внутренний JWT из проверенных
данных без расширения прав. Gateway заменяет Authorization на внутренний Bearer.
Kitchen/Order/Catalog проверяют его локально и явно передают через Feign.

У внутреннего JWT отдельные ключи/typ/aud и взаимоисключающие правила проверки
с внешним. aud задаёт разрешённых получателей этой цепочки, а не произвольное
значение клиента; каждый получатель проверяет свой audience. Подписанные sub,
roles, organizationId не берутся из доверенных на слово внешних X-User-*.
Gateway удаляет поддельные служебные заголовки, отклоняет внутренний JWT на
внешнем входе. Внутренний токен не возвращается клиенту и не пишется в логи.

TTL должен покрывать ограниченную синхронную обработку и оставаться коротким;
конкретное значение выбирается вместе с общим deadline/таймаутами, а не наугад.
exp внутреннего токена не позже exp исходного. clock skew учитывается отдельно:
нельзя унаследовать большой допуск, фактически удвоив короткий срок действия.
Нет продления токена на каждом hop и автоматического повторного обмена.

Подписанный jti/requestId полезен для корреляции, но не делает токен одноразовым.
Повторное применение похищенного Bearer возможно до exp; без хранилища replay
или отдельного доказательства владения ключом нельзя обещать его невозможность.
TLS и недоступность сервисов в обход внешней границы входят в модель развёртывания.
Локальный учебный Compose не следует выдавать за защищённую production-сеть.

Если пользователь заблокирован после выпуска внутреннего токена, допущенная
цепочка может завершиться в его срок. Новый внешний запрос не получает нового
подтверждения. Отказ Identity даёт 503 на допуске; уже допущенная бизнес-цепочка
не вызывает Identity повторно. Отдельные административные методы Identity и /me
могут читать пользователя как собственные бизнес-данные — это не повторный
сетевой validate в Kitchen/Order. Login/bootstrap имеют отдельный путь.

Остаются проверка роли, области данных, ожидаемой версии, статуса и авторства
из sub у владельца заказа. Повторная команда снова проходит локальную авторизацию
до возврата квитанции. Circuit breaker не превращает 401/403/404 в успешный ответ
или 503. Request context не хранится в общих изменяемых interceptor-полях.

5. Практика и первичные источники

AWS ALB после аутентификации подписывает user claims и отправляет JWT приложению;
приложение проверяет подпись и ожидаемого signer. ALB использует ES256 и отдельный
заголовок, поэтому заимствуется принцип, а не формат API или сторонняя технология.
Его сессии не доказывают проверку нашей БД на каждом запросе.
https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html

Cloudflare Access передаёт подписанный application JWT, который origin должен
проверять. Это второй пример передачи проверенной идентичности, не гарантия
идентичной нам семантики отзыва или сроков.
https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/

RFC 8693 описывает Token Exchange и выпуск токена для downstream. Наш внутренний
обмен не следует называть реализацией RFC без выполнения его протокола. Полный
OAuth Authorization Server для лабораторной не требуется.
https://www.rfc-editor.org/rfc/rfc8693.html

RFC 8725, 3.12 требует взаимоисключающей проверки разных типов JWT.
https://www.rfc-editor.org/rfc/rfc8725.html#section-3.12

Spring Security 6.5/Nimbus поддерживает локальную RS256-проверку, в том числе
с фиксированным открытым ключом. Новый сервис, брокер, Redis, Keycloak или
service mesh не нужны. Обновление версий зависимостей не требуется.
https://docs.spring.io/spring-security/reference/6.5/reactive/oauth2/resource-server/jwt.html

6. Проверки перед признанием реализации готовой

- На бизнес-цепочку start-cooking: один обмен и одна логическая state-check
  в Identity, ноль validate из Kitchen и Order при двух HTTP-вызовах Order.
- Новый запрос после block/change roles отклонён; уже допущенная цепочка имеет
  документированное поведение, после exp внутренний токен отклонён.
- Внешний JWT напрямую в бизнес-сервис, внутренний JWT на Gateway, неверные
  typ/aud/iss/alg/подпись/срок и поддельные заголовки не обходят проверки.
- Обмен без права вызывающего Gateway и переобмен внутреннего JWT запрещены.
- У проверяющего сервиса нет закрытого ключа; token endpoint скрыт снаружи.
- Роли/организации/changedBy, параллельные пользователи, квитанции и 401/403/404
  сохраняют прежние гарантии. Пароли/хэши/токены не выходят в ответы и логи.
- Полный Java verify, Compose, прежние бизнес-сценарии и нагрузочное сравнение:
  p95/p99, успешный throughput, ошибки, число state-check и нагрузка Identity DB.

В этом разборе production-код, ключи и активный нормативный контракт не менялись.
Новые runtime/нагрузочные тесты не запускались: нет новой реализации, которую
можно честно назвать проверенной. Изменение контракта и реализация должны
согласованно заменить перечисленные решения, а не добавиться поверх четырёх
существующих планируемых validate. L3.3 этим документом не объявляется начатым.
