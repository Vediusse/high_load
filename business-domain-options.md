## 1. Что именно требуется построить за четыре лабораторные

Ниже — рабочая декомпозиция единого ТЗ на четыре последовательных этапа. Каждый следующий этап развивает тот же продукт и сохраняет его предметную модель.

### Лабораторная 1 — модульный монолит

- REST API на Spring Boot.
- Осмысленный CRUD для основных сущностей.
- Корректные HTTP-статусы и единый человекочитаемый формат ошибок.
- Отдельные Entity и DTO.
- Валидация входных DTO на контроллере и ограничений на Entity.
- PostgreSQL в Docker и доступ через Spring Data JPA.
- Схема БД создаётся миграциями Flyway.
- Все enum хранятся строками.
- Все списки ограничены максимум 50 элементами.
- Хотя бы один список работает как бесконечная прокрутка без общего количества записей (`Slice`/keyset pagination).
- Хотя бы один список возвращает общее количество записей в HTTP-заголовке, например `X-Total-Count`.
- Не менее двух составных бизнес-операций выполняются транзакционно.
- В модели есть `One-to-Many/Many-to-One`, обычная `Many-to-Many` и `Many-to-Many` через сущность-связку с дополнительными полями.
- Общая интерактивная документация OpenAPI 3 / Swagger UI.
- Модульные и интеграционные тесты на JUnit Jupiter и Testcontainers; суммарное покрытие не ниже 70%.
- Сборка Docker-образа и запуск приложения вместе с БД через Docker Compose.
- Конфигурация передаётся через переменные окружения.

### Лабораторная 2 — микросервисная версия

- Монолит разделяется по предметным границам.
- Регистрация сервисов через Eureka.
- Централизованная конфигурация через Spring Cloud Config Server.
- Единая точка входа через Spring Cloud Gateway.
- Синхронные межсервисные вызовы через OpenFeign.
- Circuit Breaker через Spring Cloud CircuitBreaker + Resilience4j.
- Один сервис использует Reactor + R2DBC.
- Один сервис использует Reactor + Spring Data JPA/JDBC; блокирующие обращения к БД изолируются от event loop.
- Каждый сервис строится по Clean Architecture: domain, application, adapters, infrastructure.

### Лабораторная 3 — безопасность и роли

- Spring Security и JWT в заголовке `Authorization`.
- Пароли хранятся только в виде стойкого хэша и никогда не попадают в DTO ответа.
- Пользователей создаёт только роль `SUPERVISOR`.
- Доступ к операциям зависит и от роли, и от текущего пользователя: владелец работает только со своими объектами, сотрудник — только со своей площадкой или зоной ответственности.

### Лабораторная 4 — события, уведомления и файлы

- Kafka-кластер из трёх брокеров в Docker Compose.
- Несколько топиков, replication factor 3.
- Асинхронные межсервисные события применяются там, где немедленный ответ другого сервиса не нужен.
- Не менее трёх типов уведомлений.
- Отдельный файловый микросервис для загрузки и получения файлов.
- Для учебного локального запуска бинарные данные можно хранить в Docker volume, метаданные — в PostgreSQL; внешнее объектное хранилище не требуется.

## Вариант 1. Сервис управления сетью репетиционных студий

### Бизнес-модель

Небольшая сеть сдаёт музыкантам репетиционные комнаты и дополнительное оборудование по времени. Продукт ведёт доступные слоты, бронирования, комплектацию комнаты, выдачу оборудования и внутренние уведомления.

- Клиенты: музыкальные группы, преподаватели и индивидуальные исполнители.
- Плательщик: клиент, оформивший бронирование.
- Выручка: почасовая аренда комнаты и оборудования.
- Канал обслуживания: собственный веб-интерфейс поверх REST API.
- Операционный контур: администратор студии подтверждает бронь и отмечает фактическое начало/окончание визита.

### Scope

В системе есть каталог площадок, комнат, оснащения и тарифов; поиск свободных слотов; создание, подтверждение, отмена и завершение бронирования; фиксация выданного оборудования; документы и уведомления.

Не входят: онлайн-оплата, возвраты денег, интеграция с дверными замками, музыкальный стриминг, CRM-маркетинг, календарные и картографические интеграции.

### Роли

- `SUPERVISOR` — создаёт пользователей, площадки и назначает сотрудников.
- `STUDIO_MANAGER` — управляет комнатами, оборудованием и тарифами своей площадки.
- `RECEPTIONIST` — подтверждает бронь, выдаёт и принимает оборудование.
- `CUSTOMER` — видит доступность, создаёт и отменяет только свои бронирования.

### Ubiquitous language

- **Площадка** — физический адрес сети.
- **Комната** — бронируемое помещение внутри площадки.
- **Слот** — интервал потенциальной доступности комнаты.
- **Бронирование** — резерв комнаты на конкретный интервал.
- **Позиция оборудования** — оборудование, добавленное к бронированию с количеством и ценой.
- **Тарифный снимок** — цена, сохранённая в бронировании и не меняющаяся после правки каталога.

### Bounded contexts

1. **Identity & Access** — пользователи, роли, назначение на площадки.
2. **Studio Catalog** — площадки, комнаты, удобства, оборудование, тарифы.
3. **Booking** — доступность, бронирования, позиции оборудования, статусы.
4. **Operations** — выдача/возврат оборудования и акты повреждений.
5. **Notifications** — шаблоны и внутренняя лента уведомлений.
6. **Files** — метаданные, загрузка и получение договоров и актов.

В первой лабораторной это модули одного приложения; во второй — границы декомпозиции.

### Модель и связи

- `Venue` 1 → N `Room`.
- `Venue` 1 → N `EquipmentUnit`.
- `Room` M ↔ M `Amenity` — обычная Many-to-Many.
- `Customer` 1 → N `Booking`.
- `Room` 1 → N `Booking`.
- `Booking` M ↔ M `EquipmentUnit` через `BookingEquipment`; дополнительные поля: `quantity`, `hourlyPriceSnapshot`, `issuedAt`, `returnedAt`, `conditionOnReturn`.
- `Booking` 1 → N `FileReference`.

Корни агрегатов: `Venue`, `Room`, `Booking`, `User`. Значимые value objects: `TimeRange`, `Money`, `ContactData`.

### Состояния

- `BookingStatus`: `DRAFT`, `PENDING`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`.
- `EquipmentStatus`: `AVAILABLE`, `RESERVED`, `ISSUED`, `MAINTENANCE`.

### Ключевые правила

- Две активные брони одной комнаты не пересекаются по времени.
- Оборудование нельзя зарезервировать сверх доступного количества.
- Начало интервала строго раньше окончания; длительность кратна 30 минутам.
- После подтверждения цена комнаты и оборудования берётся из тарифных снимков.
- Клиент изменяет только своё `PENDING`-бронирование и не может завершить его.
- Сотрудник выполняет операции только на назначенной площадке.

### Транзакционные сценарии

1. **Подтверждение бронирования:** повторная проверка пересечения, фиксация тарифного снимка, резерв комнаты и оборудования, смена статуса, запись доменного события. Любой сбой откатывает всю операцию.
2. **Отмена бронирования:** смена статуса, освобождение комнаты и оборудования, создание события для уведомления. Частичное освобождение недопустимо.

### Списки и API

- `GET /api/rooms/{roomId}/availability?cursor=...&limit=...` — бесконечная прокрутка, без общего количества.
- `GET /api/bookings?page=...&size=...` — страничный список, `X-Total-Count` в заголовке.
- Любой `limit/size` от 1 до 50; большее значение возвращает `400 Bad Request`.

### События, уведомления и файлы

- Топики: `booking-events`, `equipment-events`, `notification-commands`.
- Уведомления: бронь подтверждена; бронь отменена; оборудование не возвращено вовремя.
- Файлы: договор аренды, акт повреждения, фотография состояния оборудования.

### Декомпозиция во второй лабораторной

- `identity-service` — JPA, JWT и роли.
- `catalog-service` — Reactor + R2DBC; площадки, комнаты, удобства, оборудование.
- `booking-service` — Reactor + JPA; доступность и бронирования.
- `notification-service` — Kafka consumer и лента уведомлений.
- `file-service` — бинарные файлы и метаданные.

## Вариант 2. Сервис проката профессионального инструмента

### Бизнес-модель

Компания сдаёт в краткосрочную аренду электроинструмент и измерительное оборудование частным мастерам и небольшим бригадам. Система управляет экземплярами, резервами, выдачей, возвратом, комплектностью и обслуживанием.

- Клиенты: частные мастера, ремонтные бригады, малые подрядчики.
- Плательщик: арендатор.
- Выручка: посуточная аренда и зафиксированные доплаты за расходники или повреждения.
- Канал обслуживания: собственный каталог и пункты выдачи.
- Операционный контур: кладовщик комплектует заказ, инспектор принимает возврат.

### Scope

В системе есть филиалы, модели и физические экземпляры инструмента, категории, комплекты, тарифы, заказы аренды, выдача, возврат, осмотр и обслуживание.

Не входят: интернет-эквайринг, доставка, GPS-трекинг, телеметрия инструмента, страховые интеграции, бухгалтерия.

### Роли

- `SUPERVISOR` — создаёт пользователей и филиалы.
- `BRANCH_MANAGER` — управляет каталогом и тарифами своего филиала.
- `WAREHOUSE_CLERK` — комплектует и выдаёт заказ.
- `INSPECTOR` — принимает возврат и фиксирует состояние.
- `RENTER` — создаёт и просматривает только свои заказы.

### Ubiquitous language

- **Модель инструмента** — карточка типа товара, например конкретная модель перфоратора.
- **Экземпляр** — физическая единица с инвентарным номером.
- **Комплект** — основной инструмент и обязательные принадлежности.
- **Заказ аренды** — согласованный период и набор экземпляров.
- **Позиция аренды** — связь заказа и экземпляра с тарифом, залогом и состоянием.
- **Осмотр** — результат проверки при выдаче или возврате.

### Bounded contexts

1. **Identity & Access** — пользователи, роли, филиалы.
2. **Rental Catalog** — модели, категории, экземпляры, принадлежности, тарифы.
3. **Rental Order** — доступность, резерв и жизненный цикл заказа.
4. **Inspection & Maintenance** — осмотры, дефекты, обслуживание.
5. **Notifications** — внутренняя лента.
6. **Files** — договоры, акты и фотографии.

### Модель и связи

- `Branch` 1 → N `ToolUnit`.
- `ToolModel` 1 → N `ToolUnit`.
- `ToolModel` M ↔ M `Category` — обычная Many-to-Many.
- `Renter` 1 → N `RentalOrder`.
- `RentalOrder` M ↔ M `ToolUnit` через `RentalLine`; дополнительные поля: `dailyRateSnapshot`, `depositAmount`, `conditionOut`, `conditionIn`, `actualReturnAt`.
- `ToolUnit` 1 → N `Inspection`.
- `Inspection` 1 → N `FileReference`.

Корни агрегатов: `ToolModel`, `ToolUnit`, `RentalOrder`, `Inspection`, `User`. Value objects: `RentalPeriod`, `Money`, `InventoryNumber`.

### Состояния

- `RentalOrderStatus`: `DRAFT`, `RESERVED`, `ISSUED`, `RETURNED`, `CANCELLED`, `OVERDUE`.
- `ToolUnitStatus`: `AVAILABLE`, `RESERVED`, `RENTED`, `INSPECTION`, `MAINTENANCE`, `RETIRED`.

### Ключевые правила

- Один экземпляр не участвует в пересекающихся активных заказах.
- Выдать можно только полностью укомплектованный `RESERVED`-заказ.
- Возврат фиксирует состояние каждой позиции; дефект переводит экземпляр в `MAINTENANCE`.
- Тариф и залог фиксируются в позиции при резерве.
- Арендатор видит и отменяет только свои невыданные заказы.
- Кладовщик не может утвердить собственный итоговый осмотр возврата; это делает инспектор.

### Транзакционные сценарии

1. **Резерв заказа:** проверка доступности всех экземпляров, создание позиций с тарифными снимками, смена статусов экземпляров и заказа, запись события.
2. **Приём возврата:** создание осмотра, обновление всех позиций, перевод исправных экземпляров в `AVAILABLE`, повреждённых — в `MAINTENANCE`, закрытие заказа и запись события.

### Списки и API

- `GET /api/tool-models?cursor=...&limit=...` — бесконечный каталог без общего количества.
- `GET /api/rental-orders?page=...&size=...` — список заказов с `X-Total-Count`.
- Фильтры: филиал, категория, статус, период; максимум 50 записей.

### События, уведомления и файлы

- Топики: `rental-order-events`, `tool-state-events`, `notification-commands`.
- Уведомления: заказ готов к выдаче; срок возврата приближается; возврат просрочен.
- Файлы: договор аренды, акт выдачи/возврата, фотография повреждения.

### Декомпозиция во второй лабораторной

- `identity-service` — JPA, JWT и роли.
- `catalog-service` — Reactor + R2DBC; модели, экземпляры и доступность.
- `rental-service` — Reactor + JPA; заказы, позиции, выдача и возврат.
- `notification-service` — Kafka consumer и лента уведомлений.
- `file-service` — бинарные файлы и метаданные.

## Вариант 3. Сервис корпоративного питания по предзаказу

### Бизнес-модель

Небольшая производственная кухня принимает от компаний групповые заказы на обеды по меню и датам. Система ограничивает приём заказов производственной ёмкостью, резервирует ингредиенты и формирует задания на приготовление и выдачу.

- Клиенты: небольшие офисы, коворкинги и учебные центры.
- Плательщик: организация-заказчик; фактическая оплата остаётся вне системы.
- Выручка: цена порций в подтверждённых заказах.
- Канал обслуживания: представитель компании оформляет предзаказ.
- Операционный контур: менеджер подтверждает заказ, производственный менеджер планирует выпуск, кладовщик списывает ингредиенты.

### Scope

В системе есть компании и точки выдачи, меню по датам, блюда, ингредиенты, рецептуры, производственные лимиты, заказы, позиции, партии приготовления и внутренние уведомления.

Не входят: курьерские маршруты, GPS, касса, эквайринг, налоговый учёт, автоматическая закупка у поставщиков, расчёт пищевой ценности внешним сервисом.

### Роли

- `SUPERVISOR` — создаёт пользователей и назначает роли.
- `ACCOUNT_MANAGER` — ведёт организации и подтверждает заказы.
- `PRODUCTION_MANAGER` — публикует меню и управляет производственными лимитами.
- `WAREHOUSE_CLERK` — принимает и списывает партии ингредиентов.
- `CLIENT_MANAGER` — создаёт заказы только своей организации и точки выдачи.

### Ubiquitous language

- **Меню дня** — набор блюд, доступных на конкретную дату.
- **Рецептура** — состав блюда и норма ингредиента на порцию.
- **Производственный лимит** — максимальное число порций блюда на дату.
- **Корпоративный заказ** — предзаказ организации к дате и точке выдачи.
- **Позиция заказа** — выбранное блюдо с количеством и ценой-снимком.
- **Партия приготовления** — задание кухне на выпуск порций.

### Bounded contexts

1. **Identity & Organizations** — пользователи, роли, компании и точки выдачи.
2. **Menu** — блюда, ингредиенты, рецептуры, меню и цены.
3. **Ordering** — заказы, позиции, дедлайны и лимиты.
4. **Production & Stock** — партии приготовления, партии ингредиентов и списание.
5. **Notifications** — внутренняя лента.
6. **Files** — спецификации, акты и документы по партиям.

### Модель и связи

- `CustomerCompany` 1 → N `DeliveryPoint`.
- `CustomerCompany` 1 → N `CorporateOrder`.
- `DailyMenu` M ↔ M `Dish` — обычная Many-to-Many.
- `Dish` M ↔ M `Ingredient` через `RecipeItem`; дополнительные поля: `quantityPerPortion`, `unit`, `isOptional`.
- `CorporateOrder` M ↔ M `Dish` через `OrderLine`; дополнительные поля: `quantity`, `unitPriceSnapshot`, `comment`.
- `ProductionBatch` 1 → N `IngredientConsumption`.

Корни агрегатов: `Dish`, `DailyMenu`, `CorporateOrder`, `ProductionBatch`, `CustomerCompany`. Value objects: `Money`, `Quantity`, `ServingDate`, `CutoffTime`.

### Состояния

- `OrderStatus`: `DRAFT`, `SUBMITTED`, `CONFIRMED`, `IN_PRODUCTION`, `READY`, `COMPLETED`, `CANCELLED`.
- `MenuStatus`: `DRAFT`, `PUBLISHED`, `CLOSED`.
- `ProductionBatchStatus`: `PLANNED`, `STARTED`, `READY`, `CANCELLED`.

### Ключевые правила

- Заказ принимается только по опубликованному меню и до времени закрытия.
- Сумма заказанных порций не превышает лимит блюда на дату.
- Цена блюда фиксируется в позиции при подтверждении.
- Запуск партии резервирует рассчитанное по рецепту количество ингредиентов.
- Представитель клиента работает только с заказами своей организации.
- Кладовщик не публикует меню, а производственный менеджер не создаёт складские поступления.

### Транзакционные сценарии

1. **Подтверждение заказа:** повторная проверка дедлайна и лимитов, фиксация цен, увеличение занятой ёмкости, смена статуса, событие подтверждения.
2. **Запуск производственной партии:** расчёт потребности по рецептурам, проверка остатков, резерв/списание всех ингредиентов, смена статуса партии, событие запуска.

### Списки и API

- `GET /api/daily-menus/{date}/dishes?cursor=...&limit=...` — бесконечная прокрутка без общего количества.
- `GET /api/orders?page=...&size=...` — список заказов с `X-Total-Count`.
- Фильтры: компания, дата, статус, точка выдачи; максимум 50 записей.

### События, уведомления и файлы

- Топики: `order-events`, `production-events`, `notification-commands`.
- Уведомления: заказ подтверждён; заказ отклонён из-за лимита; партия готова к выдаче.
- Файлы: меню-спецификация, сертификат партии ингредиента, акт расхождений.

### Декомпозиция во второй лабораторной

- `identity-service` — JPA, JWT, роли и организации.
- `menu-service` — Reactor + R2DBC; меню, блюда и рецептуры.
- `order-service` — Reactor + JPA; заказы, лимиты и ценовые снимки.
- `production-service` — JPA; партии и складские движения.
- `notification-service` — Kafka consumer и лента уведомлений.
- `file-service` — бинарные файлы и метаданные.

## Вариант 4. Сервис управления гостиницей для домашних животных

### Бизнес-модель

Небольшая гостиница принимает животных на дневное или многодневное размещение, продаёт дополнительные услуги и контролирует вместимость номеров и обязательные документы.

- Клиенты: владельцы собак и кошек.
- Плательщик: владелец животного; оплата проводится вне системы.
- Выручка: стоимость размещения и дополнительных услуг.
- Канал обслуживания: владелец оформляет заявку, администратор подтверждает размещение.
- Операционный контур: сотрудник заселяет животное, назначает услуги и завершает проживание.

### Scope

В системе есть владельцы и питомцы, корпуса и номера, характеристики номеров, периоды проживания, дополнительные услуги, назначения сотрудников, документы и уведомления.

Не входят: ветеринарная диагностика, медицинские назначения, онлайн-оплата, камеры наблюдения, трекеры, доставка животных и интеграция с государственными реестрами.

### Роли

- `SUPERVISOR` — создаёт пользователей, корпуса и назначает сотрудников.
- `HOTEL_MANAGER` — управляет номерами, услугами, тарифами и подтверждает заявки.
- `CARETAKER` — отмечает заселение, выполнение услуг и выселение.
- `OWNER` — управляет только своими питомцами, документами и заявками.

### Ubiquitous language

- **Питомец** — животное, принадлежащее владельцу.
- **Номер** — единица размещения с типом и вместимостью.
- **Проживание** — подтверждённый интервал размещения питомца.
- **Дополнительная услуга** — прогулка, груминг или индивидуальное кормление без медицинской составляющей.
- **Заказанная услуга** — связь проживания и услуги с датой, количеством и ценой.
- **Допуск** — результат проверки обязательных документов перед подтверждением.

### Bounded contexts

1. **Identity & Access** — пользователи, роли и назначения по корпусам.
2. **Customer & Pet Profile** — владельцы, питомцы и ссылки на документы.
3. **Accommodation Catalog** — корпуса, номера, характеристики, тарифы и услуги.
4. **Stay Management** — доступность, заявки, проживание, заселение и выселение.
5. **Notifications** — внутренняя лента.
6. **Files** — документы питомца, согласия и акты.

### Модель и связи

- `Owner` 1 → N `Pet`.
- `Building` 1 → N `AccommodationUnit`.
- `AccommodationUnit` M ↔ M `RoomFeature` — обычная Many-to-Many.
- `Pet` 1 → N `Stay`.
- `Stay` M ↔ M `AdditionalService` через `StayService`; дополнительные поля: `scheduledAt`, `quantity`, `unitPriceSnapshot`, `completionStatus`.
- `Pet` 1 → N `PetDocument`.
- `Stay` 1 → N `FileReference`.

Корни агрегатов: `Owner`, `Pet`, `AccommodationUnit`, `Stay`, `AdditionalService`. Value objects: `StayPeriod`, `Money`, `FeedingNote`.

### Состояния

- `StayStatus`: `DRAFT`, `PENDING_REVIEW`, `CONFIRMED`, `CHECKED_IN`, `CHECKED_OUT`, `CANCELLED`.
- `UnitStatus`: `AVAILABLE`, `OCCUPIED`, `CLEANING`, `MAINTENANCE`.
- `ServiceCompletionStatus`: `PLANNED`, `DONE`, `CANCELLED`.

### Ключевые правила

- Одно животное не имеет пересекающихся активных проживаний.
- Число одновременно размещённых животных не превышает вместимость номера.
- Подтверждение возможно только при наличии обязательного действующего документа.
- Тариф размещения и услуг фиксируется при подтверждении.
- Владелец видит только своих питомцев и их проживания.
- Смотритель отмечает услуги только в назначенном ему корпусе.

### Транзакционные сценарии

1. **Подтверждение проживания:** проверка документов и вместимости, фиксация тарифов, резерв места, смена статуса, событие подтверждения.
2. **Выселение:** завершение невыполненных назначений по правилам, освобождение места, перевод номера в `CLEANING`, закрытие проживания, событие выселения.

### Списки и API

- `GET /api/accommodation-units/available?cursor=...&limit=...` — бесконечная прокрутка без общего количества.
- `GET /api/stays?page=...&size=...` — список проживаний с `X-Total-Count`.
- Фильтры: период, корпус, статус, тип животного; максимум 50 записей.

### События, уведомления и файлы

- Топики: `stay-events`, `service-events`, `notification-commands`.
- Уведомления: проживание подтверждено; срок документа заканчивается; питомец готов к выселению.
- Файлы: документ о вакцинации, согласие владельца, акт приёма и фотография состояния при заселении.

### Декомпозиция во второй лабораторной

- `identity-service` — JPA, JWT и роли.
- `catalog-service` — Reactor + R2DBC; корпуса, номера, характеристики и услуги.
- `stay-service` — Reactor + JPA; доступность и проживание.
- `pet-service` — JPA; профили питомцев и ссылки на документы.
- `notification-service` — Kafka consumer и лента уведомлений.
- `file-service` — бинарные файлы и метаданные.

## Вариант 5. Сервис микрофулфилмента для небольших интернет-магазинов

### Бизнес-модель

Небольшой склад хранит товары локальных продавцов и выполняет их заказы: принимает поставку, размещает остатки, резервирует товар, формирует задание на сборку и фиксирует передачу подготовленной посылки перевозчику без интеграции с его API.

- Клиенты: локальные интернет-магазины и продавцы маркетплейсов.
- Плательщик: продавец.
- Выручка: учётная стоимость хранения, приёмки и обработки заказов; фактические расчёты остаются вне системы.
- Канал обслуживания: кабинет продавца и рабочее место склада.
- Операционный контур: приёмщик размещает поставку, комплектовщик собирает заказ, контролёр закрывает отгрузку.

### Scope

В системе есть продавцы, товары, склады и ячейки, поставки, остатки, заказы на исполнение, позиции, резервирование, задания на сборку, упаковка и передача перевозчику.

Не входят: витрина интернет-магазина, приём оплаты от покупателей, интеграции с маркетплейсами и перевозчиками, маршрутизация, печать на физическом принтере, прогнозирование спроса.

### Роли

- `SUPERVISOR` — создаёт пользователей, склады и назначения.
- `SELLER_MANAGER` — создаёт товары, поставки и заказы только своего продавца.
- `RECEIVER` — принимает поставки и размещает товар.
- `PICKER` — выполняет назначенные задания на сборку.
- `SHIPMENT_CONTROLLER` — проверяет комплектность и закрывает отгрузку.

### Ubiquitous language

- **SKU** — товарная позиция конкретного продавца.
- **Ячейка** — адрес хранения внутри склада.
- **Остаток** — количество SKU в ячейке с разбивкой на доступное и зарезервированное.
- **Поставка** — ожидаемый и фактически принятый набор товаров.
- **Заказ на исполнение** — запрос продавца собрать набор SKU.
- **Позиция заказа** — SKU, количество и стоимость обработки-снимок.
- **Задание на сборку** — назначенная сотруднику операция отбора из конкретных ячеек.

### Bounded contexts

1. **Identity & Tenancy** — пользователи, роли, продавцы и назначения на склады.
2. **Product Catalog** — SKU, категории и признаки хранения.
3. **Inbound & Inventory** — поставки, ячейки, остатки и складские движения.
4. **Fulfillment** — заказы, резервирование, задания на сборку и отгрузка.
5. **Notifications** — внутренняя лента.
6. **Files** — упаковочные листы и акты расхождений.

### Модель и связи

- `Seller` 1 → N `Sku`.
- `Warehouse` 1 → N `StorageCell`.
- `Sku` M ↔ M `ProductCategory` — обычная Many-to-Many.
- `FulfillmentOrder` M ↔ M `Sku` через `FulfillmentOrderLine`; дополнительные поля: `requestedQuantity`, `reservedQuantity`, `handlingPriceSnapshot`.
- `Sku` M ↔ M `StorageCell` через `StockBalance`; дополнительные поля: `availableQuantity`, `reservedQuantity`, `version`.
- `FulfillmentOrder` 1 → N `PickTask`.
- `InboundDelivery` 1 → N `InboundLine`.

Корни агрегатов: `Seller`, `Sku`, `InboundDelivery`, `StockBalance`, `FulfillmentOrder`, `PickTask`. Value objects: `Quantity`, `Money`, `CellAddress`.

### Состояния

- `InboundStatus`: `DRAFT`, `EXPECTED`, `RECEIVING`, `ACCEPTED`, `CANCELLED`.
- `FulfillmentOrderStatus`: `DRAFT`, `SUBMITTED`, `RESERVED`, `PICKING`, `PACKED`, `SHIPPED`, `CANCELLED`.
- `PickTaskStatus`: `NEW`, `ASSIGNED`, `IN_PROGRESS`, `DONE`, `CANCELLED`.

### Ключевые правила

- SKU уникален в пределах продавца, но не глобально.
- Доступный остаток не может быть отрицательным; зарезервированное количество не превышает физический остаток.
- Заказ резервируется целиком либо не резервируется вовсе.
- Комплектовщик видит только назначенные ему задания и не закрывает отгрузку.
- Менеджер продавца не видит товары и заказы другого продавца.
- Отгрузка возможна только после выполнения всех заданий и проверки комплектности.

### Транзакционные сценарии

1. **Приёмка поставки:** сверка строк, увеличение остатков по нескольким ячейкам, создание движений, фиксация расхождений, смена статуса поставки, запись события.
2. **Резервирование заказа:** блокировка нужных остатков, резерв всех строк, создание заданий на сборку, смена статуса заказа, запись события. При нехватке одной позиции откатывается весь резерв.

### Списки и API

- `GET /api/skus?cursor=...&limit=...` — бесконечная прокрутка каталога без общего количества.
- `GET /api/fulfillment-orders?page=...&size=...` — список заказов с `X-Total-Count`.
- Фильтры: продавец, склад, статус, период; максимум 50 записей.

### События, уведомления и файлы

- Топики: `inventory-events`, `fulfillment-events`, `notification-commands`.
- Уведомления: поставка принята с расхождением; заказ зарезервирован; заказ собран и готов к передаче.
- Файлы: упаковочный лист, акт расхождений поставки, фотография повреждённой упаковки.

### Декомпозиция во второй лабораторной

- `identity-service` — JPA, JWT, роли и принадлежность продавцу.
- `catalog-service` — Reactor + R2DBC; SKU, категории и поиск.
- `inventory-service` — JPA; поставки, ячейки, остатки и движения.
- `fulfillment-service` — Reactor + JPA; заказы, резервирование и задания.
- `notification-service` — Kafka consumer и лента уведомлений.
- `file-service` — бинарные файлы и метаданные.

## 3. Нейтральное сравнение вариантов

| Вариант | Главный объект | Главная конкуренция | Складской контур | Временные интервалы | Документы |
|---|---|---|---|---|---|
| Репетиционные студии | Бронирование комнаты | Пересечение броней | Лёгкий: оборудование | Да | Договор, акт повреждения |
| Прокат инструмента | Заказ аренды | Резерв одного экземпляра | Средний: экземпляры | Да | Договор, акт осмотра |
| Корпоративное питание | Заказ порций | Производственный лимит | Средний: ингредиенты | Дата и дедлайн | Спецификация, сертификат партии |
| Гостиница для животных | Проживание | Вместимость номера | Нет | Да | Документ питомца, акт приёма |
| Микрофулфилмент | Заказ на исполнение | Конкурентный резерв остатка | Полный | Нет | Упаковочный лист, акт расхождений |

Все пять вариантов рассчитаны на одну команду, локальный Docker Compose и минимальные внешние расходы. В каждом варианте присутствуют реальные клиенты, продаваемая услуга, операционный процесс и достаточная предметная сложность для всех требований четырёх лабораторных.

## 4. Критерии выбора одного варианта

Выбирать следует не по стеку — он одинаков и полностью фиксирован, — а по тому, какую предметную область команде будет проще защищать и развивать весь семестр:

1. Насколько команде понятны термины и бизнес-правила без длительного исследования отрасли.
2. Какой основной конкурентный конфликт интереснее реализовать: слот, экземпляр, лимит производства, вместимость или остаток.
3. Нужен ли складской учёт и насколько глубоко команда хочет в него заходить.
4. Какие роли проще демонстрировать преподавателю на сквозном сценарии.
5. Какие файлы и уведомления выглядят естественно, а не добавлены ради формального требования.

После выбора следующими артефактами должны стать: контекстная диаграмма, ER-модель, список REST-контрактов, таблица прав доступа и план реализации лабораторной 1.
