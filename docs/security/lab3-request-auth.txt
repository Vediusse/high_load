Допуск запроса и явная передача JWT — 2026-10-09

Изменение по решению пользователя: одна проверка актуальности пользователя
на новый внешний бизнес-запрос вместо validate на каждом сервисном входе.
Это реализация среза аутентификации. L3.4 добавил проверяемую матрицу ролей
на входах бизнес-сервисов. L3.5 применяет границу организации представителя
до pagination/count, берёт организацию при создании заказа из проверенного JWT
и сохраняет sub в changedBy переходов статуса. Действуют роли Identity, SUPERVISOR на actuator/info и
защищённая проверка организации для Identity; бизнес-API требуют внутренний JWT.

Путь запроса:
Client -- external HS256 Bearer --> Gateway
Gateway -- external Bearer + Gateway credential --> Identity exchange
Identity -- чтение текущего пользователя --> Identity PostgreSQL
Identity -- internal RS256 JWT --> Gateway
Gateway -- internal Bearer --> Kitchen -- тот же Bearer --> Order
Order -- локальная подпись/claims и обработка --> Kitchen --> Gateway --> Client

Внутренний обмен: POST /internal/v1/auth/exchange. Он не публикуется Gateway.
Identity проверяет credential вызывающего, внешний JWT и текущего пользователя.
Gateway использует WebClient с discovery, таймаутом подключения 1s и общим 2s,
без повторов, включая отключённый transport retry при обрыве TCP. Ошибка токена
401; недоступность/некорректный обмен 503.
Выданный JWT дополнительно проверяется Gateway перед передачей дальше.

Для start-cooking Kitchen по-прежнему сначала читает Order, затем отправляет
команду. Оба Feign-вызова передают тот же внутренний Bearer; ни один не вызывает
Identity. Для замены позиций и submit Order передаёт Bearer в Catalog.
Principal захватывается из @AuthenticationPrincipal в конкретном запросе;
JPA/Feign остаются в BlockingRequests. Interceptor с общим токеном/ThreadLocal
не используется. Fallback сохраняет security 401/403 по HTTP-статусу и
распознанный бизнес-404. Тело 401 может отсутствовать у стандартного транспорта
Feign; отказ авторизации не зависит от успешного разбора JSON и не становится 503.
Контекст ограничения транспорта: https://github.com/spring-cloud/spring-cloud-openfeign/issues/506

Профили:
- внешние JWT: HS256, aud corporate-catering-api, прежний срок 15 минут;
- внутренние: RS256, typ catering-internal+jwt, iss corporate-catering-internal,
  срок 30 секунд, допуск часов 2 секунды, exp не позже внешнего exp;
- aud внутреннего JWT — фиксированный список Gateway и четырёх прикладных
  сервисов. Каждый проверяет собственное имя. Это не токен на один endpoint;
  роль и область данных проверяются отдельно;
- внутренний JWT не обменивается заново и не принимается на внешнем входе;
- sub/roles/ver/organizationId берутся из проверенных данных, новый jti не
  означает одноразовость и не заменяет защиту от повторного использования.

Граница доверия: общий aud включает весь внутренний контур, поэтому любой сервис,
который получил этот bearer, может передать его другому сервису списка до exp.
JWT связывает user claims с подписью Identity, но не аутентифицирует текущий
service caller. Текущая модель предполагает доверенную сеть и авторизацию каждой
операции на стороне сервиса-владельца. Для изоляции по принципалу понадобятся
audience/token на конкретный downstream API и проверяемая service identity.
Такой token exchange — установленный стандартный паттерн: RFC 8693 описывает
subject-token/resource/audience exchange; Microsoft Entra OBO показывает API A,
которое обменивает token A на token B для API B. Наш endpoint — собственный
неполный протокол по мотивам этого паттерна, он не реализует RFC 8693 или OBO.

После блокировки/смены ролей следующий внешний запрос отвергается. JWT проверяется
на входе каждого HTTP-вызова: уже начавшийся handler не прерывается по exp, но
новый downstream вызов с истёкшим Bearer получит 401. Автоматического продления
в рамках запроса нет: для долгой самостоятельной операции нужен ограниченный
срок выполнения, а для следующего вызова — новый внешний допуск и exchange.
При отказе Identity новые запросы получают 503, внутренние ранее допущенные
запросы проходят локальную проверку без обращения к Identity.
Identity сохраняет прямой приём внешнего JWT для своих API с локальной DB-проверкой;
для внутреннего JWT Security не читает БД повторно. /me читает актуальные данные
пользователя как собственную бизнес-операцию. Устаревший validate удалён:
Gateway и бизнес-сервисы его не использовали.

Identity проверяет привязку через GET /internal/v1/organizations/{id} в Order.
Endpoint требует SUPERVISOR; совмещение с ролью представителя сохраняет границу
организации. Ответ содержит только id/active. Вызов не возвращается через Gateway.

Конфигурация:
- JWT_SECRET_BASE64 — внешний HMAC-секрет, только Identity;
- INTERNAL_JWT_PRIVATE_KEY_BASE64 — RSA PKCS8 DER в Base64, только Identity;
- INTERNAL_JWT_PUBLIC_KEY_BASE64 — соответствующий RSA X509 DER в Base64,
  Identity/Gateway/Catalog/Order/Kitchen;
- GATEWAY_EXCHANGE_SECRET — Base64 минимум 32 случайных байт, только Gateway/Identity.
Пара RSA минимум 2048 бит; ключи проверяются на старте и должны совпадать.
Значения задаются через env, .env игнорируется Git. Config Server не получает
значения секретов. Генерация RSA доступна через openssl genpkey -algorithm RSA
-pkeyopt rsa_keygen_bits:2048; для приватного DER используйте openssl pkcs8
-topk8 -nocrypt -outform DER, публичного — openssl pkey -pubout -outform DER.
Полученные DER кодируются base64 без переводов строки и сохраняются в .env
с правами 0600. Не публикуйте ключи/credential/токены в терминальном выводе или Git.
Рабочие значения проверочного стенда сохранены только в игнорируемом окружении.

Тесты:
- Common: реальные RS256 JWT, локальная проверка и ролевые отказы, неверные
  issuer/audience/type/claims/срок, подмена подписи, неоднозначные заголовки;
- Gateway: один обмен на запрос, замена Bearer, удаление поддельных заголовков,
  внутренние маршруты 404, отсутствие токена, 401 vs 503, повреждённый ответ,
  обрыв TCP без повторного допуска;
- Identity: одно чтение состояния при обмене и отсутствие повторов на внутренних
  вызовах, credential Gateway, запрет переобмена, ограничение exp, блокировка;
- прежние PostgreSQL/API/транзакционные проверки работают с подписанными тестовыми
  JWT, а не с отключённой security;
- scripts/lab3-authentication.py проверяет реальные сервисы, внутренний Kitchen
  вызов Order, новые/ранее допущенные запросы при блокировке и паузе Identity,
  затем полный сценарий лабораторной 1 и совместимость OpenAPI;
- scripts/lab3-identity.py сохраняет проверки пользователей/ролей/схемы/топологии;
- Postman business-scenarios: переменная accessToken для Bearer, baseUrl — Gateway;
  для текущего среза полный сценарий запускается от SUPERVISOR;
- lab1-defense.sh и lab2-api-contract.py принимают необязательный AUTH_TOKEN:
  без него сохраняют сценарий лабораторий 1-2, с ним проверяют защищённый Gateway.

Результаты текущего запуска фиксируются в AI/state/L3.3-request-auth/ и отчёте
AI/state/L3.3-request-auth-report.md. Функциональные тесты не доказывают рост
throughput; нагрузочные p95/p99 не измерялись и не заявляются.

Команды (Java 21, работающий Docker):
  JAVA_HOME="$(/usr/libexec/java_home -v 21)" ./mvnw clean verify
  docker compose up -d --build --wait

Для отдельного тестового Compose-стенда экспортируйте bootstrap/exchange значения
из его приватного файла окружения. Выполняйте последовательно: первый скрипт
временно приостанавливает Identity для проверки отказа:
  python3 scripts/lab3-authentication.py http://localhost:18082 <compose-project>
  python3 scripts/lab3-identity.py http://localhost:18082
Сценарий с приостановкой Identity предназначен только для отдельного тестового стенда.
