Корпоративное питание. Архитектура лабораторной 2

Статус решений

Это завершённая архитектура второй лабораторной для утверждённой бизнес-модели:
собственная кухня, корпоративные предзаказы, постоянное меню, ручное решение кухни.
Здесь нет запланированных обязательных переделок, заглушек и параллельного монолита.
Технологии последующих лабораторных в реализацию не входят.

1. Границы и владельцы

catalog-service — меню, категории, активность и текущие цены; PostgreSQL catalog.
order-service — организации, точки, заказ, позиции, снимки цен, история и квитанции
команд кухни; PostgreSQL orders. Только Order изменяет состояние заказа.
kitchen-service — приготовление и локальная рабочая проекция KitchenTask;
собственная PostgreSQL. Kitchen не хранит изменяемую копию состава заказа.
gateway-service — единственная опубликованная точка HTTP-входа.
discovery-service — Eureka, регистрация и поиск экземпляров.
config-service — Spring Cloud Config Server, централизованная конфигурация.
common — обычная библиотека технического кода с условной автоконфигурацией;
не запускается отдельно, не содержит бизнес-Entity, репозитории или сетевые DTO.

Организации и точки остаются внутри Order: в этом продукте это справочники
заказчика, а не самостоятельная CRM. Проверка принадлежности и активности
выполняется локально, без ещё одной сетевой зависимости при оформлении заказа.
Пакет organization отделён от order. Отдельный сервис организаций не требуется.
Подключение реальной внешней CRM не является требованием этой лабораторной.

Каждый владелец имеет свою БД, пользователя и Flyway-историю. Нет общих таблиц,
межбазовых FK, чтения чужих репозиториев и зависимостей Maven между бизнес-сервисами.
Ссылки на внешние объекты — UUID. Снимок названия и цены принадлежит заказу после
submit. Изменение каталога не переписывает оформленный заказ.

2. Сетевой граф и контракты

REST-клиент -> Gateway -> Catalog / Order / Kitchen
Kitchen -> Order -> Catalog

Циклических бизнес-вызовов нет. Order не вызывает Kitchen. Публичные команды
start-cooking, mark-ready, complete Gateway направляет только в Kitchen.
Подтверждение, отклонение и отмена проходят через Order. Без Kitchen внешний
клиент не может обойти контур приготовления и напрямую изменить эти статусы.

Order -> Catalog:
  POST /internal/v1/dishes/snapshots
  Пакетное чтение актуальных активных блюд для редактирования и отправки заказа.
  Внутренний контракт принимает не больше 1000 UUID за один вызов. Больший
  набор Order разбивает на пакеты и проверяет полноту каждого ответа. Изменение
  заказа начинается только после успешного получения всех пакетов; дополнительного
  ограничения на количество позиций в публичном DTO нет.

Kitchen -> Order:
  GET  /internal/v1/orders/{id}              текущее состояние заказа;
  GET  /internal/v1/orders/kitchen            страница активной очереди;
  POST /internal/v1/orders/states             до 50 кратких состояний;
  POST /internal/v1/orders/{id}/kitchen-commands  идемпотентная команда.

Внутренние пути не публикуются Gateway и не входят в публичный Swagger.
Рабочая очередь кухни доступна внутреннему контуру через
GET /internal/v1/kitchen/tasks. Публичное чтение заказов менеджером остаётся
GET /api/v1/orders с фильтром status; публичный API первой лабораторной сохранён.

Feign-клиенты находятся в:
  order-service/.../catalog/client/CatalogClient.java
  kitchen-service/.../kitchen/client/OrderClient.java
Реакции на отказ и проверка ответа — в CatalogGateway и OrderGateway.
DTO партнёра принадлежат клиенту. В Kitchen они лежат в kitchen/client/dto,
а не в пакете Entity чужого сервиса. Совпадение полей JSON — контракт, а не общая
доменная модель или зависимость от JAR владельца данных.

Имена catalog-service/order-service — логические идентификаторы Eureka.
При обычном запуске Feign получает адрес экземпляра через discovery и LoadBalancer.
Для изолированного теста или заданного адреса существуют clients.catalog.url и
clients.order.url. В коде нет IP-адресов развёртывания. /v1 — версия протокола;
её нельзя произвольно менять настройкой одного клиента без смены контракта сервера.

3. Транзакции, конкуренция и отказ

Catalog использует WebFlux, Reactor и Spring Data R2DBC. Flyway использует JDBC
только при старте. SQL-операции внутри HTTP-цепочки неблокирующие.
Order использует WebFlux и JPA. Kitchen использует WebFlux, JPA и Feign.
JPA и блокирующий Feign выполняются через ограниченный boundedElastic scheduler;
транзакция открывается и закрывается в одном синхронном сервисном вызове.
Entity никогда не возвращается из контроллера; наружу идёт DTO.

Состав, сумма, статус и история заказа меняются в локальной транзакции Order.
Версия агрегата защищает от параллельного изменения. При замене состава строка
сохраняет ID, если блюдо осталось в заказе; меняется количество. Версия увеличивается
и при изменении состава с прежней суммой. Ошибка БД откатывает всю операцию.

При submit цена повторно читается из Catalog. Неуспешный вызов не меняет DRAFT.
После submit используются только сохранённые снимки. Распределённой транзакции
между базами нет и для этого сценария она не нужна.

Feign: connect timeout 1 секунда, read timeout 2 секунды, без автоматических
повторов изменяющей команды. Spring Cloud Circuit Breaker + Resilience4j считает
транспортные ошибки и некорректные ответы. Известные бизнес-ошибки сохраняют свой
HTTP-код и не открывают circuit. Открытый circuit возвращает 503.
Gateway ограничивает ожидание ответа 10 секундами. JPA-транзакции имеют настраиваемый
timeout, по умолчанию 5 секунд; ожидание соединения Hikari ограничено 5 секундами.
Переполненный scheduler даёт 503. Fallback не возвращает выдуманный бизнес-успех.
X-Trace-Id проходит через Gateway, Reactor, блокирующий поток и Feign.

Повтор одной команды приготовления имеет стабильный commandId, вычисленный из
заказа, действия и expectedVersion. Order сериализует дубликаты advisory lock внутри
транзакции и сохраняет JSON-ответ вместе с изменением заказа. Точный повтор возвращает
исходный ответ даже после следующих переходов. Повтор commandId с другим содержимым
даёт 409. Это не делает произвольные разные бизнес-команды идемпотентными.

Если Order выполнил команду, но ответ потерялся или Kitchen не смог сохранить
проекцию, клиент получает ошибку и повторяет ТОТ ЖЕ запрос с прежней expectedVersion.
Квитанция не позволяет выполнить переход дважды; проекция восстанавливается.
Ошибка связи сама по себе не означает, что удалённая транзакция не состоялась.

KitchenTask — восстанавливаемая проекция. Состояние с меньшей версией не может
перезаписать новое. Чтение очереди всегда запрашивает актуальную страницу у Order.
За одно чтение дополнительно сверяется один пакет максимум из 50 ранее известных
активных задач, самые давно проверенные первыми. Повторное наблюдение обновляет
время проверки и не позволяет одним задачам постоянно вытеснять остальные.
Отмена вне запрошенной страницы будет отражена при следующих чтениях очереди.
Полного сетевого обхода всех задач внутри одного HTTP-запроса нет. Пустая страница
не трактуется как отмена отсутствующих в ней заказов. Ошибка пакета не подделывает
пустую очередь. Без обращений к очереди отдельный фоновый процесс не запускается.

4. Инфраструктура и конфигурация

Шесть приложений и три PostgreSQL поднимаются штатным compose.yaml. Наружу открыт
только Gateway; Config, Eureka, бизнес-сервисы и БД доступны внутри Docker-сети.
У всех девяти контейнеров есть health checks. Конфигурация приложения централизована
в config-service/src/main/resources/config-repo. Native/classpath backend Config
Server — выбранный законченный способ хранения конфигурации для лаборатории.
Его изменение применяется через пересборку Config Server и перезапуск клиентов;
динамический refresh настроек не заявлен.

Пароли берутся из окружения. Compose завершается с понятной ошибкой, если пароль
одной из БД не задан. .env не отслеживается Git и не попадает в Docker build context.
.env.example содержит названия переменных, но не действующие пароли.
Порт Gateway задаёт HTTP_PORT. Адреса Config/Eureka и баз, учётные данные,
параметры scheduler, Feign и circuit можно переопределить конфигурацией окружения.
Числа по умолчанию в конфигурации — эксплуатационные настройки, а не ветвление
бизнес-логики под конкретную машину.

Для существующих данных намеренно сохраняются:
  - физическая kitchen DB с именем production и volume production-postgres-data;
  - namespace production:v1: в исторических идентификаторах команд;
  - тексты ранее применённых Flyway-миграций.
Логические сервисы, классы, таблицы и пути называются Kitchen. Исторические имена
не являются временной заготовкой: их смена нарушила бы совместимость с данными
или идемпотентность. Изменения схемы добавляются новыми миграциями.

5. Запуск и проверка

Java 21 и Docker требуются для сборки и интеграционных тестов.
При первом запуске:

  cp .env.example .env
  В .env установить три пароля. Если 8080 занят, установить HTTP_PORT=18080.
  ./mvnw clean verify
  docker compose up --build -d --wait

Не запускать --remove-orphans в старом проекте монолита и не удалять старые volumes.
Имя нового Compose-проекта по умолчанию corporate-catering; COMPOSE_PROJECT_NAME
в .env позволяет сохранить имя ранее запущенного проекта и его volumes.
Для существующих баз сохранить их действующие пароли: изменение .env само по себе
не меняет пароль внутри PostgreSQL. Параметр -p позволяет проверить чистый стенд
независимо от существующих данных.

  Импортировать postman/business-scenarios.postman_collection.json.
  baseUrl = http://localhost:<HTTP_PORT>; Run collection, 1 iteration, delay 0.

Коллекция содержит 65 видимых запросов и создаёт собственные данные; нет скрытых
HTTP-запросов, дополнительных environment-файлов или обязательного Newman runner.
Default baseUrl в ней — localhost:18080 для локального запуска рядом с первой лабой.
Проверка повторной команды кухни требует именно второй лабораторной.

Дополнительные проверки (вместо corporate-catering указать своё COMPOSE_PROJECT_NAME):
  scripts/lab2-infrastructure.sh corporate-catering http://localhost:18080
  scripts/lab2-topology.py corporate-catering http://localhost:18080
  scripts/lab2-catalog.sh corporate-catering http://localhost:18080
  scripts/lab2-kitchen.py corporate-catering http://localhost:18080

Последние два скрипта намеренно останавливают зависимость и восстанавливают её;
запускать их на проверочном стенде. Они не заменяют быстрый Postman-прогон.
Старый публичный контракт: docs/baseline/openapi.json, проверка — lab2-api-contract.py.

6. Соответствие второй лабораторной

Eureka, Config, Gateway -> инфраструктурные приложения + Compose/проверка регистрации.
Feign/Circuit Breaker -> два клиента и gateway-обёртки + отказные тесты и реальные
остановки зависимостей.
Reactor + R2DBC -> CatalogService + CatalogApiIT с PostgreSQL Testcontainers.
Reactor + JPA -> OrderService/BlockingRequests + ReactiveExecutionIT и интеграционные
тесты транзакций, версий, отката и повторов.
Отдельные данные -> три Flyway-схемы + проверка топологии.
Неизменность бизнеса -> API baseline, регрессия первого сценария и Postman.
Полная реализация -> реальные REST, PostgreSQL, Feign; заглушки используются только
как HTTP-партнёры внутри тестов инъекции отказов.

Выбранные подходы согласуются с документацией используемых технологий:
  Feign: логическое имя, discovery, URL override и конечные таймауты:
  https://docs.spring.io/spring-cloud-openfeign/reference/spring-cloud-openfeign.html
  Reactor: изоляция блокирующего вызова через fromCallable и boundedElastic:
  https://projectreactor.io/docs/core/release/reference/faq.html
  Приватное владение данными каждого сервиса, доступ через API:
  https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice

Версии зафиксированы в pom.xml: Java 21, Spring Boot 3.5.16, Spring Cloud 2025.0.3.
Совместимость веток Boot 3.5.x / Cloud 2025.0.x: https://spring.io/projects/spring-cloud/

7. Проверенная версия, 25 сентября 2026

Полный ./mvnw clean verify: 90 тестов, без ошибок и пропусков. Порог JaCoCo 70%
пройден во всех модулях; покрытие бизнес-сервисов 95–98% строк.
Проверены штатный Compose, Config/Eureka, изоляция трёх баз и единственный внешний
Gateway, 32 публичные операции и прежние DTO, полный сценарий первой лабораторной.
Postman: два прогона на отдельном стенде (130 запросов, 288 проверок), затем один
на обновлённом основном (65 запросов, 144 проверки); все успешны.
Остановки Catalog, Order и Kitchen проверены с восстановлением; недоступность БД
Order и Catalog даёт 503. Проверены отсутствие частичного изменения, параллельные
повторы и восстановление circuit. При обновлении сохранены содержимое всех десяти
бизнес-таблиц и ответы исторических команд; миграция Kitchen V3 применена успешно.
