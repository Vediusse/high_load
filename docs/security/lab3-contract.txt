L3.1 — контракт безопасности
Версия для проверки, 2026-10-09. Это целевой контракт, ещё не реализация.
База: feature/lab3, L3.0 принят пользователем. Production-код здесь не меняется.

Редакция механизма аутентификации 2026-10-09 по прямому решению пользователя.
Одна проверка актуальности на внешний запрос и внутренний RS256 JWT заменяют
прежний план validate на каждом сервисном входе. Реализация/проверки описаны
в lab3-request-auth.txt; первоначальное обоснование — lab3-request-auth-review.txt.

1. Источники и принятые уточнения

Артефакты/06-безопасность-события-и-файлы.md: Аутентификация, Содержимое JWT,
Матрица прав, Проверки текущего пользователя.
Артефакты/04-rest-api.md: Пользователи — лабораторная 3.
AI/high-load-lab-3/references/{requirements,design,stages}.md.
Фактический API: docs/baseline/lab3-endpoints.tsv и контроллеры сервисов.

Основной артефакт задаёт одну роль KITCHEN_MANAGER для подтверждения,
отклонения, приготовления и выдачи. Фраза «подтверждение и приготовление
требуют разных ролей» в архитектурном пересказе противоречит этой матрице:
новую роль не вводим, применяем первичную матрицу прав.
У supervisor нет заданного административного правила чтения заказов:
отдельное право не добавляем; без бизнес-роли чтение заказов запрещено.
Бизнес-статусы, транзакции и правила отмены остаются прежними.

2. Роли и области данных

Ровно четыре RoleCode: SUPERVISOR, ORGANIZATION_REPRESENTATIVE,
CLIENT_MANAGER, KITCHEN_MANAGER. UserStatus: ACTIVE, BLOCKED.
Сокращения далее: OR — ORGANIZATION_REPRESENTATIVE, CM — CLIENT_MANAGER,
KM — KITCHEN_MANAGER.
Пользователь может иметь несколько ролей. Разрешённые операции — объединение
прав назначенных ролей. SUPERVISOR не наследует бизнес-роли.
При наличии ORGANIZATION_REPRESENTATIVE организация ограничивает ВСЕ
операции этого пользователя над организациями, точками и заказами, даже
при дополнительных бизнес-ролях. Дополнительная роль не снимает границу
организации. Меню является общим и не имеет organizationId.

Матрица каждой операции: lab3-permissions.tsv. Любая неперечисленная
операция запрещена по умолчанию. Разрешение роли не отменяет бизнес-проверки.

Представитель читает свою организацию, её точки, заказы и историю; изменяет
только свои заказы. Фильтр organizationId добавляется в запрос к БД до
пагинации и COUNT: страницы и X-Total-Count не раскрывают чужие записи.
Чужой ID или явно чужой organizationId-фильтр: 404 RESOURCE_NOT_FOUND.
CM без роли представителя работает со всеми организациями: отдельной модели
«обслуживаемых организаций менеджера» в текущей системе нет.
KM без роли представителя читает заказы кроме DRAFT; списки и total содержат
только доступные статусы. Это позволяет видеть SUBMITTED для принятия решения
и историю уже обработанных заказов. Изменение состава ему не разрешено.
При совмещении CM+KM право CM на чтение DRAFT сохраняется; если есть роль
представителя, ограничение организации применяется поверх этого объединения.

CreateOrderRequest сохраняет поля organizationId, deliveryPointId,
requestedDeliveryAt, comment. Для представителя organizationId необязателен:
значение берётся из проверенной identity; совпадающее значение принимается
для совместимости, несовпадающее даёт 404. Для CM без роли представителя
organizationId обязателен, отсутствие — 400 VALIDATION_FAILED. Проверка
принадлежности deliveryPoint выполняется владельцем данных в обоих случаях.

Чужие точка, заказ и история дают такой же 404, как отсутствующий объект.
Роль проверяется раньше поиска объекта: запрещённая роль получает 403,
независимо от существования ID. После ролевой проверки проверяется область,
затем expectedVersion, статус и остальные инварианты.

3. Публичный identity API и DTO

POST /api/v1/auth/login: LoginRequest(login, password) -> 200 TokenResponse.
POST /api/v1/users: CreateUserRequest -> 201 UserResponse, Location.
GET /api/v1/users/{id}: 200 UserResponse.
GET /api/v1/users?page=0&size=20: 200 PageResponse<UserResponse>, size 1..50,
стабильная сортировка по id. Дополнительный total здесь не требуется.
PUT /api/v1/users/{id}/roles: UpdateUserRolesRequest -> 200 UserResponse.
POST /api/v1/users/{id}/block: без тела -> 200 UserResponse; повтор идемпотентен.
GET /api/v1/me: 200 CurrentUserResponse текущего активного пользователя.
Все операции над /users требуют SUPERVISOR, /me — любую активную роль.

LoginRequest: login — непустая строка; password — непустая строка.
CreateUserRequest: login, password, roles, organizationId.
  login: 3..64 ASCII символов [A-Za-z0-9._-], trim и lowercase (Locale.ROOT)
  до поиска/сохранения, уникальность обеспечивается БД.
  password: 12..72 байта UTF-8 при создании, без trim/нормализации;
  login-проверка не навязывает заново минимальную длину создания.
  roles: непустой набор уникальных значений только из четырёх RoleCode.
  organizationId: UUID обязателен при роли представителя. При создании
  без этой роли поле должно отсутствовать/null (иначе 400).
UpdateUserRolesRequest: только roles, те же правила набора.
UserResponse и CurrentUserResponse: id UUID, login, status, roles,
organizationId (null без активной роли представителя).
TokenResponse: accessToken, tokenType="Bearer", expiresAt (UTC ISO-8601).
Ни один response не содержит password/passwordHash. Токен не содержит login.
Входные DTO с паролем не используют автоматически сгенерированный toString,
который выводит пароль. Тело login/users и Authorization не логируются.

Привязка представителя устанавливается при создании и не переносится на
другую организацию API этого этапа. Снятие роли сохраняет прежнюю привязку
в Identity DB, но убирает её из JWT/response и не даёт прав представителя.
Вернуть роль можно после повторной проверки привязанной организации.
Назначить роль представителя пользователю без сохранённой привязки:
422 ORGANIZATION_REQUIRED. DTO roles не расширяем скрытым organizationId;
для нового представителя используется существующий POST /users.
Проверяется существование организации через Order, не через чужую БД.
Неактивная организация: 422 ORGANIZATION_INACTIVE; отсутствующая: 404.
Сбой проверки организации: 503, пользователь/роли не сохраняются частично.

Хранение: BCrypt через Spring PasswordEncoder, strength=12 как выбранная
настройка проекта; соль генерирует encoder. Хэш только в Identity DB.
Bootstrap: отдельные env IDENTITY_BOOTSTRAP_LOGIN/PASSWORD, без значений
по умолчанию и без открытого bootstrap endpoint. Создание начального
SUPERVISOR только при пустой таблице пользователей; повторный старт ничего
не перезаписывает, заблокированного пользователя не реактивирует. После
первого создания секрет bootstrap убирается из окружения. Отсутствие env
на пустой БД останавливает старт с ошибкой без печати значений.

4. Два профиля JWT и отзыв доступа

Решение пользователя 2026-10-09 заменяет validate на каждом сервисном входе:
одна проверка актуальности на новый внешний запрос, затем локальное подтверждение
внутреннего JWT в сервисах. Используются Spring Security Resource Server/Nimbus.
Это внутренний обмен приложения, не реализация OAuth Token Exchange RFC 8693.

Внешний access JWT:
- HS256, секрет JWT_SECRET_BASE64 минимум 32 случайных байта только у Identity;
- iss corporate-catering-identity, aud corporate-catering-api, typ JWT;
- sub UUID пользователя, roles, organizationId только при роли представителя,
  iat/exp/jti и целочисленная неотрицательная ver;
- срок JWT_ACCESS_TTL=15m, допуск JWT_CLOCK_SKEW=30s; прежняя строгая проверка
  типов, issuer/audience, exp > iat, iat не в будущем, nbf при наличии;
- пароль, хэш, login и контактные данные в токен не включаются.

Внутренний JWT:
- RS256, отдельная пара RSA минимум 2048 бит. Закрытый PKCS8-ключ только Identity;
  публичный X509-ключ у Identity, Gateway, Catalog, Order, Kitchen;
- env INTERNAL_JWT_PRIVATE_KEY_BASE64 и INTERNAL_JWT_PUBLIC_KEY_BASE64;
- iss corporate-catering-internal, typ catering-internal+jwt;
- фиксированный aud доверенного контура: gateway-service, identity-service,
  catalog-service, order-service, kitchen-service. Каждый проверяет свой aud;
  это не отдельный токен на маршрут, полномочия задают проверяемые роли/область;
- sub/roles/ver/organizationId копируются только из проверенного внешнего JWT;
  iat и jti выпускаются заново, exp=min(now+30s, external.exp), допуск 2s;
- валидатор ограничивает срок теми же 30s и проверяет обязательные claims;
- отдельные ключи, алгоритмы, typ и audience исключают подмену профилей.

Граница доверия этого учебного варианта: aud содержит весь внутренний контур.
Поэтому сервис, получивший внутренний Bearer, может передать его другому сервису
из этого списка до exp; подпись доказывает, что Identity выпустила claims, но не
личность сервиса, который отправил текущий HTTP-запрос. Это подходит только при
доверенной внутренней сети и самостоятельной авторизации в каждом владельце API.
Это осознанное упрощение, не утверждение о production-best practice. Для более
строгой изоляции каждому downstream API нужен отдельный aud/token и проверенная
идентичность вызывающего сервиса (например, OAuth client credential или mTLS).
RFC 8693 задаёт стандартный протокол обмена с resource/audience и subject token;
Microsoft Entra OBO документирует реальный flow API A -> токен для API B.
Наш `/internal/v1/auth/exchange` — собственный упрощённый контракт, не реализация
RFC 8693/OBO и не криптографическая защита от захвата уже выданного bearer.

Нельзя просто включить HS256 и RS256 в один общий доверенный профиль. Gateway
принимает снаружи только внешний JWT; бизнес-сервисы — только внутренний.
Identity поддерживает оба для своих пользовательских API: внешний проверяет
через собственную БД, внутренний — локально. Его /me дополнительно читает
актуальную пользовательскую модель как бизнес-данные, а не сетевой validate.

Изменение ролей и первая блокировка повышают version; старый внешний JWT
не проходит НОВЫЙ допуск Gateway/Identity после commit. JWT проверяется на входе
каждого HTTP-вызова, а не непрерывно: уже начавшийся handler продолжит работу и
после exp. Но новый межсервисный HTTP-вызов с тем же Bearer после exp будет
отклонён. Снятие роли не прерывает уже допущенную цепочку.
Повторный внешний запрос, включая повтор бизнес-команды, требует нового обмена.
Никакого кэша допусков внешних запросов или автоматического продления внутреннего
JWT нет. Долгие операции должны укладываться в TTL либо получать новый токен через
явный повторный допуск на отдельный вызов; продлевать JWT посреди уже начатого
запроса нельзя. Подписанный jti не гарантирует одноразовость: похищенный Bearer может
быть повторно использован внутри контура до истечения срока.

5. Gateway, обмен, межсервисный доступ и реактивность

Gateway до аутентификации скрывает /internal/** (404 независимо от токена),
удаляет X-User-*, X-Roles, X-Organization-Id, X-Auth-* и X-Gateway-Credential
без учёта регистра. X-Trace-Id служит только корреляции. Неоднозначные несколько
Authorization отвергаются. Нет trusted identity из обычных внешних заголовков.

Для нового защищённого запроса Gateway выполняет ровно один HTTP-вызов:
POST /internal/v1/auth/exchange в Identity с Authorization: Bearer <external JWT>
и собственным X-Gateway-Credential. GATEWAY_EXCHANGE_SECRET — отдельные минимум
32 случайных байта Base64, только у Gateway и Identity; это credential процесса,
не новая пользовательская роль. Нет тела с произвольными sub/roles/audience.
Identity сначала проверяет credential постоянновременным сравнением, затем
подпись/claims и ACTIVE/ver/roles/organizationId пользователя в своей БД.
Одна логическая проверка состояния не обещает ровно один SQL-запрос загрузки.

Успех: 200 InternalTokenResponse(accessToken, tokenType=Bearer, expiresAt).
Identity не выпускает подтверждение из внутреннего JWT и не продлевает его.
Ответ никогда не выдаётся внешнему клиенту и не логируется. Gateway локально
проверяет полученное подтверждение и заменяет Authorization при маршрутизации.
Ошибочный внешний токен даёт 401. Невалидный ответ обмена, сбой Identity или
неверная конфигурация credential дают клиенту 503; нет пропуска по старому
состоянию. Connect timeout 1s, общий timeout 2s, без автоматических retry.

Все следующие сервисные входы проверяют внутренний JWT локально. Они не вызывают
Identity для validate. Без внутреннего JWT или с внешним JWT — 401. С валидным
токеном сервис отдельно проверяет роль, область данных и бизнес-инварианты.
Недоступность Identity не останавливает уже допущенную бизнес-цепочку, но новые
внешние запросы получают 503. Приватная сеть не заменяет проверку подписи.

Feign принимает Authorization явным параметром @RequestHeader:
- Kitchen -> Order: тот же внутренний Bearer для get/queue/states/command;
- Order -> Catalog: тот же внутренний Bearer для snapshots;
- Identity -> Order: внутренний Bearer для GET /internal/v1/organizations/{id},
  ответ только {id,active}, роль SUPERVISOR. Дополнительная роль представителя
  сохраняет ограничение организации. При прямом внешнем запросе в Identity
  внутренний токен выпускается локально после его собственной проверки БД.

Login остаётся публичным и идёт прямо в Identity без предварительного обмена.
Три health endpoint доступны анонимно. Внутренние вызовы идут напрямую через
discovery, без повторного прохода Gateway и без новых credentials пользователя.

Principal передаётся из @AuthenticationPrincipal, авторизация живёт в реактивном
SecurityContext. Нужный Bearer захватывается в конкретном вызове BlockingRequests
и явно передаётся по service-методам в Feign. Нет чтения SecurityContextHolder
из общего interceptor/ThreadLocal, глобального actor или изменяемого singleton
с текущим токеном. JPA/Feign/BCrypt/RSA-подпись выполняются вне event loop;
Gateway вызывает Identity через WebClient. Catalog сохраняет Reactor/R2DBC.

Fallback CatalogGateway/OrderGateway сохраняет 401/403 по HTTP-статусу даже без
тела ответа (особенность стандартного транспорта Feign), а 404 — по ApiError;
они не становятся 503 и не учитываются circuit как отказ зависимости. Сетевой
сбой или некорректный ответ дают 503. Владелец Order проверяет доступ до возврата
квитанции повторной команды; changedBy для этапа L3.5 берётся из проверенного sub.
Полная бизнес-матрица L3.4/L3.5 не считается выполненной одним введением JWT.

TLS требуется для внешнего развёрнутого стенда и передачи секретов обмена/
Bearer между узлами. Локальный Compose HTTP остаётся учебным стендом. Секреты
не попадают в Config Server, Git, логи, actuator и пользовательские DTO. Новый
Authorization Server, брокер, Redis, Keycloak и service mesh не добавляются.

6. Технические маршруты и анонимный доступ

Исчерпывающий анонимный allowlist на конечном L3.6:
  POST /api/v1/auth/login;
  GET /actuator/health;
  GET /actuator/health/liveness;
  GET /actuator/health/readiness.
Health отдаёт только status, без подробностей и секретов.
Swagger/OpenAPI не анонимны: любой активный пользователь может получить
/v3/api-docs, /v3/api-docs/catalog, /v3/api-docs/kitchen, /v3/api-docs/identity,
/v3/api-docs/swagger-config, /swagger-ui.html и /swagger-ui/** с Bearer.
Swagger UI открывается клиентом, который добавляет Bearer и к HTML/assets,
а Authorize задаёт токен для бизнес-запросов; анонимная веб-страница входа
и cookie-сессия не добавляются. Для обычной демонстрации без браузерного
плагина используются Postman или защищённый OpenAPI через curl с Bearer.
GET /actuator/info — только SUPERVISOR, минимум сведений о конфигурации.
Другие actuator endpoints не экспонируются. Анонимное OPTIONS не добавляем:
отдельного cross-origin frontend нет. HTTP Basic/form login выключены,
CSRF выключен для API с Bearer без cookie, HTTP session не создаётся.
Неизвестные пути: без токена 401, с валидным токеном 404; /internal/** через
Gateway всегда 404. Известный ресурс с неподдерживаемым методом после
аутентификации даёт 405; matcher роли не должен случайно разрешать метод.

Config Server и Eureka сохраняют доступность внутри приватной Compose-сети,
без JWT для config fetch, регистрации и heartbeat. Их служебные HTTP API
не публикуются на хост и не маршрутизируются Gateway. Это явная граница
доверенной инфраструктуры, не утверждение, что сеть заменяет security
бизнес-сервисов. БД также не публикуются. Публичный HTTP допустим только
в локальной лабораторной; внешний развёрнутый стенд требует TLS.

7. Ошибки и проверка контракта

Сохраняем ApiError {code,message,fieldErrors,traceId} и X-Trace-Id в ответе.
401 AUTHENTICATION_REQUIRED: отсутствующий/невалидный/устаревший JWT,
  заблокированный/удалённый пользователь. WWW-Authenticate: Bearer.
401 INVALID_CREDENTIALS: login, одинаковые код/сообщение для неверного
  пароля, неизвестного логина и блокировки. Dummy password hash check для
  отсутствующего пользователя, без обещания строгого постоянного времени.
403 ACCESS_DENIED: активный пользователь, но нет нужной роли.
404 RESOURCE_NOT_FOUND: чужой или отсутствующий объект.
400 VALIDATION_FAILED/MALFORMED_JSON: DTO, неизвестная роль, неверный UUID.
409 LOGIN_ALREADY_EXISTS: нормализованный login занят.
422 ORGANIZATION_REQUIRED/ORGANIZATION_INACTIVE: ограничения привязки.
503 DEPENDENCY_UNAVAILABLE: невозможно выполнить новый допуск identity
  или организацию; это не неверный пароль и не отказ роли.

SecurityWebFilterChain использует общий формат через authentication entry
point/access denied handler: RestControllerAdvice один не покрывает фильтры.
Проверки до контроллера не должны терять traceId. Ошибки не печатают токен,
пароль или хэш. Сценарии проверки и ожидаемые результаты — lab3-checks.tsv.
Каждый ряд permissions проверяется: разрешённая роль/область; без токена;
все остальные одиночные роли; чужой объект для ограниченной роли. Ряд с
несколькими разрешёнными ролями проверяется для каждой, включая SUPERVISOR
без бизнес-роли и совмещение ролей с границей организации.

8. Переходы между контрольными точками

L3.1 не добавляет ни один описанный endpoint/DTO в production.
В L3.2 Identity сразу защищает свои /users и /me, вводит контролируемый
bootstrap и внутреннюю проверку JWT. Бизнес-API пока остаются на базовой
линии. Временный вызов проверки организации через существующий Order API
допустим только как явно отмеченный адаптер до закрытия бизнес-API.
К L3.3 внутренний контракт проверки организации должен заменить этот вызов;
иначе supervisor без CM потеряет возможность создать представителя.
Временное исключение аутентификации бизнес-API удаляется в L3.3;
временные исключения авторизации не могут пережить L3.4/L3.5.
Каждая точка имеет свой отчёт; отсутствие защиты на промежуточной точке
не считается готовой безопасностью всей лабораторной.
